Product case study

ReliefSync: automating disaster relief coordination

A Salesforce-based system that matches relief requests with volunteers and supplies, with no manual dispatching.

B.Tech minor project, JECRC UniversityTeam of 2My role: testing & QASalesforce Flow Builder2025–26

TL;DR

Relief teams often coordinate through calls, sheets and paperwork, so requests sit unattended and volunteers get double-booked. ReliefSync centralizes requests, volunteers and supplies in one system, and a record-triggered flow decides what happens the moment a request is created. In testing, all 12 test cases passed, including shortage and duplicate-assignment scenarios.

1. The problem

In an emergency, someone has to answer three questions fast: Do we have the supplies? Is anyone free? Who is going? Done manually, this causes:

  • Delayed response, because coordinators check stock and availability by hand.
  • Double-booked volunteers and over-promised supplies.
  • No single view of what is pending, assigned or stuck.

Goal: shorten the time from “request raised” to “help assigned” and remove the common failure modes without adding coordinator workload.

3. The solution

Four linked objects hold the data. When a Relief Request is created, a record-triggered flow checks stock, checks volunteers and acts on the result.

  1. A new relief request is created and the flow starts automatically.
  2. Is resource quantity above 0? If not, status becomes Waiting for Resource.
  3. Is a volunteer available? If not, status becomes Waiting for Volunteer.
  4. An Assignment record is created.
  5. The volunteer is set to Busy.
  6. Resource quantity is reduced by 1.
  7. Request status becomes Assigned.

Data model: Assignment is a junction object linking one Request, one Volunteer and one Resource (one-to-many from each parent).

Skill matching, location matching, mobile access

Won’t have (for now)

AI prioritization, government system integration, payments

6. Key decisions and trade-offs

  • Declarative automation over code. Flow Builder let two students ship quickly and keeps the logic readable by non-developers. Trade-off: less flexibility at scale.
  • Availability-only matching. The v1 flow considers whether a volunteer is free, not their skills or distance. That kept the logic testable but means a High-severity request is not yet handled ahead of a Low one.
  • Check stock before volunteers. It gives a clear status when either is missing, which is what a coordinator needs to act on.

7. Testing and results (my contribution)

I owned the testing process: I designed and ran 12 manual test cases covering the happy path (assignment, status, stock reduction), shortages (no resource, no volunteer), duplicate prevention and data consistency. All passed after debugging flow configuration issues. Observed flow execution was a few seconds end to end on a Developer Edition org; this was small-scale testing, not a load test.

10. What I learned

  • Turning a messy operational process into explicit rules (BRD/FRD style) is most of the work; the tooling is the easy part.
  • As the tester, I saw that edge cases (no stock, no volunteers, busy volunteers) define the product as much as the happy path, and that testing the flow turned up configuration bugs early.
  • Scoping v1 tightly made the system testable, and an honest limitations list gave a clear roadmap.
